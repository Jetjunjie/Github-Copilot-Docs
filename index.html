先看这 10 条：最快提升效率的使用习惯

目标不是少用 Copilot，而是把它用在最合适的地方：小问题快速问，明确改动直接改，复杂任务先规划，大上下文只在真正需要时使用。

默认策略

  • 日常问答、API 查询、语法修正：先用 Auto 或 mini 类经济模型。
  • 普通编码、重构、测试修复：使用主力通用模型，先明确验收标准。
  • 架构、安全、跨模块复杂问题：先用高阶模型做 Plan，再切回较便宜模型执行。
  • 输出默认要求短：3 bullets max、code only、table format。

最贵反模式

  • 一句“帮我优化一下项目”直接开 Agent，让它探索 20 步。
  • 长会话一直不断，历史上下文滚到数万 token 仍继续追问。
  • 全局启用一堆 MCP/插件工具，每一步 Agent 都重新发送工具 Schema。
  • 把 copilot-instructions.md 写成 Wiki，长期常驻加载大量低价值规则。
黄金公式：先 Ask 明确问题 → Plan 固化方案和验收标准 → Agent 只执行小范围任务 → 长会话及时总结重开 → 定期优化个人配置。

理解 AI Credits：账单不是只算你打的字

Usage-Based Billing 后，Copilot 的 Chat、Agent、CLI、Code Review 等智能交互会按模型 token 价格折算为 AI Credits。传统代码补全和 Next Edit Suggestions 仍属于核心开发体验，通常不按这类 Chat/Agent token 消耗计入。

输入

你看到的提示词只是冰山一角

每次请求前还会叠加系统提示、仓库指令、文件上下文、对话历史、工具描述和终端输出。真正的大头常常不是用户输入。

输出

输出通常更贵

多家模型的输出价格通常是输入的 4–8 倍。让模型少写废话，比把用户提示词从 50 token 压到 30 token 更有价值。

池化

Gross 与 Billed 的差异

Gross usage 可表示已消耗的基础池 AI Credits；Billed amount 为 0 往往意味着还在包含额度或共享池内，尚未触发额外预算。

消耗来源为什么会变贵用户可控动作
对话历史每轮把前面上下文继续带上，长会话可能累计到数万 token。主题切换、问题解决、上下文很长时总结后新开会话；CLI 中及时 /clear。
文件上下文自动带入相邻文件、显式引用大文件、整仓探索都会放大输入。只引用必要文件；先问“需要哪些文件”再喂上下文；大文件截取相关函数。
工具 SchemaMCP/插件工具描述在 Agent 每一步都可能被重新发送。按工作区启用工具；不用的 MCP 关闭；避免全局启用所有工具。
终端输出安装日志、测试日志、diff、lockfile、目录列表会产生大量低信号文本。使用压缩输出；让命令安静运行；只把失败片段、关键堆栈和摘要给 Copilot。
输出文本回答越长，成本越高；解释型回答尤其容易膨胀。要求“只给代码”“最多 3 点”“表格输出”“先结论后一行理由”。

模型选择：不要把所有任务都交给最贵模型

高阶模型的价值在于处理不确定性、跨域推理和关键决策；一旦方案明确，执行阶段通常可以切到更便宜的模型。最优实践是“规划用强模型，执行用经济模型”。

模式选择：Ask、Edit、Plan、Agent 不是同一个价格档

模式决定调用次数、工具使用、上下文扩张速度。先选最便宜且足够完成任务的模式，而不是默认把所有问题都交给 Agent。

Completion / NES

边写边补

适合局部代码补齐、下一步编辑建议、重复样板。无需解释、不需要多文件推理时优先使用。

Ask

问清楚

适合解释、查 API、比较方案、定位思路。一次调用成本低，是 Agent 前的低成本澄清阶段。

Edit / Inline Chat

小范围改

适合单文件或选中代码改写。比 Agent 更可控，避免工具链和仓库探索带来的额外 token。

Agent

端到端执行

适合多文件、需要跑命令、需要验证的任务。必须给范围、验收标准、最大轮次和输出上限。

如果你还说不清“完成等于什么”，先不要开 Agent

先用 Ask 让 Copilot 帮你把问题拆成文件、步骤、风险和验收标准。

如果只改一个函数，不要让 Agent 扫全仓

选中代码用 Inline Chat/Edit；告诉它只改这一段，保留公共接口。

如果要跨文件执行，先 Plan 后 Agent

让 Agent 读取计划文件或按计划执行，减少探索和返工。

上下文治理：把“永远加载”的东西变小

Token 优化的核心不是少写提示词，而是减少每一轮都会重复带上的固定成本。仓库指令、MCP 工具、历史、终端输出都要治理。

指令分层

常驻只放风格、命名、输出限制等高频规则；模块约定用 applyTo 限定路径；低频流程用 slash command 或文档按需引用。

---
applyTo: "src/api/**/*.ts"
---
API conventions:
- Validate with zod.
- Return { data, error } envelope.
- Handlers stay thin.

新会话卫生

超过 20 轮、主题切换、已解决问题、上下文接近占满时，让 Copilot 先产出 handoff summary，然后新开会话继续。

Summarize current state for a new session:
- goal
- decisions
- files changed
- remaining tasks
- commands already run
10 bullets max.

工具最小化

MCP 按工作区启用，不要全局打开。任务不需要 Slack/Jira/数据库/浏览器工具时关闭，避免每步发送 Schema 税。

Agent constraints:
- Use only file read/edit and test command.
- Do not call browser or external APIs.
- Max 12 turns.
- Stop if acceptance criteria unclear.
AGENTS.md / copilot-instructions.md 不要写成百科。如果 Agent 能通过读代码自己推断，就不要写进去。只保留“踩坑会出事故”的规则：例如必须用某包管理器、部署需要 VPN、迁移必须按顺序、认证模块禁止顺手重构。

提示词高级写法：高密度、强约束、少废话

“短”不一定便宜，“信息密度”才便宜。把自然语言散文改成结构化需求、类型签名、伪代码、表格约束，通常更省也更准。

从散文改成任务规格

低密度:
Could you please help me create an endpoint that accepts user data and validates fields...

高密度:
POST /api/users
Validate:
- name: string, required
- email: string, required, email
400: { errors }
201: { data: user }
Persist to DB. Add tests.

输出上限要写进每次任务

Answer format:
- Start with final recommendation.
- Max 5 bullets.
- Include code diff only if needed.
- No background explanation.
- If blocked, state exact blocker.
目标推荐指令适用场景
只要实现Code only, no explanation.需求明确、只缺代码。
快速判断Yes or no, then one line why.方案选择、风险判断。
限制冗长3 bullets max.日常问答、总结。
结构化对比Table format: option, when to use, tradeoff.模型、架构、方案比较。
减少返工Ask clarifying questions only if required to avoid wrong implementation.需求不清但希望保持进度。
避免大范围改动Touch only these files. Do not refactor unrelated code.生产代码、风险控制。
语言选择：技术提示词可优先使用英文，尤其是 API、代码、类型、错误信息；中文说明也可以，但关键约束建议保留代码原生表达。中文在部分模型上 token 效率接近英文，但英文生态代码语料更稳定。

插件、CLI、GitHub Copilot App：不同入口适合不同工作

入口不同，默认上下文、工具权限和消耗模式也不同。把任务放到最合适的入口，既省 token 也省时间。

使用方式最适合Token 风险高端用法
IDE 插件：VS Code / Visual Studio / JetBrains 代码补全、Inline Chat、局部 Edit、Agent 改代码、测试修复。 自动文件上下文、长会话、终端输出、工具列表可能放大。 先选中相关代码再问；开启终端输出压缩；用 applyTo 指令；任务结束新开会话。
GitHub Copilot CLI / gh 扩展 命令行解释、生成 shell 命令、仓库自动化、预算/用量脚本。 CLI/Agent 可能反复跑命令并吞入长日志。 命令加 quiet 参数；只贴错误摘要；高消耗时避免重复大上下文 CLI 任务。
GitHub Copilot App 独立使用 Copilot Chat、整理思路、生成提示词、做轻量技术问答和任务规划。 如果把它当成长会话工作台，历史上下文会持续增长；如果反复粘贴大段日志或代码，也会放大消耗。 用于澄清需求、拆解任务、生成可带回 IDE 的计划；复杂实现回到 IDE 插件或 CLI 中执行。
Copilot Coding Agent 从 issue 自动开分支、提交 PR、处理明确任务。 任务描述模糊时会探索、跑命令、重试，消耗不可预测。 issue 模板写清验收标准、不可改范围、测试命令、最大实现范围。
入口选择口诀：能补全就别 Chat，能 Inline Edit 就别 Agent，能 Ask 清楚就别让 Agent 猜，能小 PR Review 就别全仓扫描。

Agent 高阶技巧：把探索变成执行，把失控变成可控

Agent 不是“更聪明的 Chat”，而是会多轮调用模型、读取文件、执行命令和使用工具的工作流。它的价值高，但必须有边界。

好 Agent 提示词

Goal:
Implement user-level budget display in admin page.

Scope:
- Only src/admin/billing/**
- Do not change auth or routing

Acceptance:
- Shows gross, billed, remaining
- Handles missing budget explicitly
- Existing tests pass

Process:
1. Inspect relevant files only
2. Propose short plan
3. Implement
4. Run targeted tests

Output:
Final summary only, max 5 bullets.

坏 Agent 提示词

帮我看看这个项目哪里可以优化，
顺便修一下有问题的地方，
最好性能和架构都提升一下。

问题：范围无限、验收标准缺失、容易全仓探索、输出冗长、返工概率高。

Agent 成本控制点建议效果
最大轮次复杂任务设置 10–20 轮；不清楚时先停下来问。防止无穷探索和重复命令。
工具权限只允许本任务需要的工具；MCP 按 workspace 启用。减少 Schema 税和误调用风险。
终端输出使用 quiet/no-progress；只回传失败片段和关键摘要。减少日志噪声进入上下文。
任务切片把“大迁移”拆成 schema、API、UI、测试几个 PR。降低单次上下文和返工成本。
验证命令提前写清 targeted test，不让 Agent 自己猜。减少跑错命令、装错依赖、重复验证。

个人与团队建议：让好习惯变成默认工作方式

Copilot 的收益来自持续使用，也来自持续优化。把模型选择、上下文管理、Agent 边界和输出格式变成团队共识，能同时提升交付速度、质量和可控性。

按工作类型分层

日常开发、复杂重构、架构评审、学习问答适合不同模型和模式。不要把所有任务都套进同一种工作流。

复盘高消耗任务

记录任务入口、模型、模式、文件范围、工具调用和是否重复执行。复盘一次高消耗任务，通常能形成多次复用的优化习惯。

建立默认规则

把常用提示词模板、仓库指令、Agent 范围约束和 Review 范围写成团队默认规则，减少每个人重复摸索。

优化动作建议做法观察信号
配置回顾检查 MCP、instructions、模型默认值、Agent 使用频率。重复工具调用减少，长会话减少。
实践分享沉淀 Plan→Agent、上下文切片、输出控制、PR Review 范围的示例。返工次数减少，任务完成更稳定。
模板复用把高频场景做成可复制提示词模板。同类任务输出更一致。
任务拆分把大范围重构、大 PR、大日志诊断拆成小批次。Agent 轮次更少，Review 更聚焦。

按用户画像制定 Copilot 使用策略

同一个预算策略不适合所有人。真正可持续的 Copilot 推广，需要把用户按任务复杂度、Agent 频率、代码影响范围和业务关键性分层。

高消耗场景诊断矩阵

当 Copilot 的一次任务明显比预期更慢、更长或更消耗时，通常可以从模式、上下文、工具和输出四个维度定位原因。

症状：Agent 一跑就烧得快

  • 常见原因：任务模糊、轮次过多、全仓探索、MCP 工具过多、终端日志过长。
  • 快速修复：先 Plan；限制目录和文件；设置最大轮次；关闭无关工具；只跑 targeted tests。
  • 观察信号：模型、模式、执行步数、工具调用、涉及文件数、终端输出规模。

症状：Chat 越聊越慢、越聊越贵

  • 常见原因：历史过长、主题混杂、大文件反复引用、没有总结重开。
  • 快速修复：让 Copilot 生成 handoff summary；新建会话；只贴关键片段。
  • 观察信号：轮次数、上下文文件、是否多主题、是否重复解释。

症状：Code Review 消耗高

  • 常见原因：PR 太大、全量 review、多次重复 review、要求解释所有风格问题。
  • 快速修复：按目录分批；只审 security/performance/breaking changes/test gaps。
  • 观察信号：PR 文件数、diff 行数、review 次数、审查范围。

症状：CLI/终端任务消耗高

  • 常见原因：安装日志、测试日志、Docker 输出、lockfile diff、progress bar 进入上下文。
  • 快速修复：使用 quiet/no-progress；保留失败堆栈；不要把完整日志喂给模型。
  • 观察信号：命令、输出行数、是否重复运行、是否可复现。
优先做三个动作：缩小上下文、限制输出、拆分任务。大多数高消耗场景都能通过这三步先降下来，再决定是否需要更换模型或模式。

明天就能开始的行动清单

按收益优先级排序。最先做 1、3、6，通常最快看到效果。

  • 压缩仓库指令：把 copilot-instructions.md 从 Wiki 改成“地雷清单 + 输出规则”。
  • 默认输出上限：在个人或仓库指令里加入短输出规则，如 3 bullets max、code only。
  • 盘点 MCP 和插件：关闭不用的服务器和工具，按工作区而不是全局启用。
  • 先 Ask 后 Agent：验收标准说不清时，先让 Copilot 产出计划和文件清单。
  • 默认经济模型：日常任务用 Auto/mini/主力模型，高阶模型只做复杂规划和关键审查。
  • 使用 applyTo 指令：把 API、DB、UI、测试规则拆成路径限定文件，避免每轮全量加载。
  • 建立新会话习惯：长会话总结后重开；CLI/Agent 主题切换时清上下文。
  • 终端安静输出：让测试、构建、安装命令使用 quiet/no-progress，只把失败摘要给模型。
  • Code Review 分范围：大 PR 按目录、风险类型、变更类型分批审。
  • 每月复盘：结合 AI Credit 用量、用户角色、任务入口和模型选择调优预算策略。

常见问题 FAQ

是不是越短的提示词越省？

不一定。真正重要的是信息密度。删掉客套话有帮助，但如果因为太短导致模型误解、反复追问或返工，反而更贵。

什么时候值得用高阶模型？

当任务涉及架构、安全、跨模块复杂决策、未知问题排查时值得用。建议只用于规划和关键判断，执行阶段切回主力或经济模型。

Budget 能不能解决消耗过快？

Budget 是风险护栏，不是优化手段。它能防止超支，但不会让同样任务更省；模型路由、上下文治理和 Agent 约束才会降低单任务消耗。

为什么同样一句话，Agent 比 Chat 贵？

Agent 可能多轮调用模型、读取文件、执行命令、调用工具，并在每一步带上工具 Schema 和历史上下文；Chat 通常是更少轮次的直接问答。

Code Review 应该怎么省？

不要让模型审所有风格问题。限定风险类型、限定目录、分批审大 PR，并要求只输出真实 blocker 或高风险问题。

如何判断一种用法是否值得保留？

看它是否能稳定减少返工、缩短交付时间、降低上下文膨胀，并且在同类任务里可重复使用。
